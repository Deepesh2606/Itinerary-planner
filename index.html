Q1 · ALGORITHM Why did you use K-Means for day planning instead of just sorting attractions?
Simple sorting by rating ignores geography, resulting in the user traversing the entire city multiple times a day. K-Means clusters attractions by geographic coordinate proximity (lat, lng), guaranteeing that Day 1 is concentrated in one borough, Day 2 in another, minimizing transit overhead.
Q2 · TIME COMPLEXITY What is the time complexity of 2-Opt and why not use exact Branch-and-Bound TSP?
Standard TSP brute-force is O(N!), which is NP-hard and crashes the Node.js event loop even for 12 places (12! = 479 million combinations). 2-Opt heuristic runs in polynomial time O(N²) per iteration, yielding 95%+ optimal paths in under 5 milliseconds on typical daily stop sizes (N ≈ 4 to 7).
Q3 · RESILIENCY & BILLING How do you handle Google Places API quotas and external service failures?
We implement a 2-Tier Caching Layer in MongoDB with a 7-day TTL index. When a city search runs, we query our internal database first. Only missing POIs trigger upstream Google API calls. We also have mock JSON fallback seeds for live viva demos so the presentation never fails even if offline.
Q4 · REAL-WORLD LOGIC How does the Weather-Adaptive swapping rule work?
When the user requests an itinerary, the backend checks OpenWeather 5-day forecast. If Rain Probability > 60% for a specific day, the optimizer flags outdoor stops (parks, open viewpoints) and swaps them with nearest high-rated indoor counterparts (museums, covered galleries, aquariums) tagged with isIndoor: true.
Q5 · SYSTEM DESIGN How does "Regenerate Single Day" work without resetting the whole trip?
The endpoint POST /api/trips/:id/regenerate-day takes the target `dayNumber`, locks the places allocated to other days, pulls new candidate POIs from the pool, and re-executes 2-Opt TSP strictly on that single day array, updating only `trip.days[targetIndex]` in MongoDB.
